# v0.4.1 Current-Glucose Freshness Hotfix

## Gate status

The v0.4.0 phone acceptance exposed a critical freshness defect: the phone could continue to
display a much older persisted Nightscout reading even though the upstream service had newer data.
This document records the scoped investigation and the v0.4.1 fix. It intentionally contains no
personal glucose values, server addresses, credentials, screenshots, or unsanitized logs.

The failed v0.4.0 engineering artifact remains a separate historical artifact and evidence record.
The fix is versionName `0.4.1`, versionCode `5`. After automated verification, the only next step
is a new phone physical acceptance test; this hotfix does not unlock another milestone.

## Root cause

The accepted pre-v0.4 Nightscout path made one bounded current request. The v0.4 planner introduced
90-day history backfill and changed the cold-cache path to request seven-day ranges before issuing
the current request. A range response that failed, exceeded the response limit, or otherwise could
not be parsed aborted that provider read before the current endpoint was reached. The repository
then retained the old Room row, so a restart or manual retry repeated the same gate and continued
to expose the old timestamp.

The v0.4 current request also used an `If-Modified-Since` validator. A `304 Not Modified` was
treated as a successful cache response, which was an independent way for an old cache to look like
a successful refresh. Conditional validators are not safe for the time-sensitive current snapshot.

The UI, Room observation, coaching, notification, Wear payload, and watch-face paths did not select
the old value independently. They consumed the repository's selected latest row. The defect was in
provider request ordering and cache/persistence gating, not in the phone display formatter.

## Refresh path traced

1. `MainActivity` passes the refresh callback to the phone Compose UI.
2. The **Refresh now** action calls `PhoneViewModel.refresh()`.
3. `PhoneViewModel` calls `PhoneRefreshCoordinator.refresh(refreshProviders = true)`.
4. The coordinator calls `GlucoseRepository.refresh()` before generating the coaching snapshot and
   publishing the existing Wear `WatchState`.
5. `GlucoseRepositoryImpl` asks the selected provider for a current snapshot first, persists that
   snapshot to Room immediately, then asks for the requested history.
6. `NightscoutProvider` calls the current `/api/v1/entries/sgv.json` request without a conditional
   validator. It normalizes valid records, merges by `(sourceId, id)`, and publishes the newest
   measured timestamp.
7. Historical range requests run after current persistence. A range failure is best effort and
   cannot block or regress the current cache/state.
8. `GlucoseDao.observeLatestForSource` selects the maximum measured timestamp for the active
   source prefix, with deterministic ID ordering for equal timestamps.
9. `PhoneViewModel` observes that Room flow and computes display age from the reading timestamp and
   the current clock. On current failure, the cached row remains visible with its naturally
   increasing stale age while provider/repository status reports the failure.
10. The coordinator publishes the same normalized reading through the existing Wear Data Layer;
    no Wear, coaching, notification, or watch-face contract changed.

## Fix invariants

- A successful current request is persisted before history work starts.
- Historical backfill never overwrites the current-state pointer with an older record.
- If current and history complete in either order, the newest valid record for that source wins.
- Duplicate and out-of-order records are resolved deterministically by source identity, measured
  timestamp, received timestamp, and stable value fields.
- Configured Nightscout servers remain isolated by source identity; one server cannot replace
  another server's current row.
- Current refreshes do not use conditional HTTP validators. An unexpected `304` is a failed current
  refresh, not a cache hit.
- Current failures retain the persistent cache and publish an explicit failure state. The UI age is
  still calculated from the original measurement timestamp.
- Wear payloads, coaching decisions, notifications, quick actions, and watch-face resources are
  unchanged.

## Regression coverage

The data tests cover:

- current data plus older backfill data, with current winning;
- backfill completion before or after current completion;
- stale runtime cache followed by a successful current refresh;
- current persistence before a history failure;
- duplicate/out-of-order deterministic selection;
- source-isolated server switching;
- current request behavior without conditional validators and explicit handling of `304`;
- retry, cache retention, parser normalization, and oversized-response behavior.

The full GitHub Actions run is the release gate. Its summary records the v0.4.1 commit, run ID,
certificate continuity, APK hashes, ZIP hash, and five-file package contract. The old v0.4.0 run is
not overwritten or relabeled.

## Safety boundary

This is a data freshness and synchronization correctness fix. It does not diagnose, treat, dose
medication, or make a medical claim. Until the new phone physical acceptance test passes, the
milestone remains open.
